# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`clinical-genogram` is a Stencil.js (v4) web-component library that renders an interactive clinical genogram (family tree) as hand-rolled SVG. It has zero runtime dependencies; `jspdf` is an optional, lazily imported peer for PDF export. Public usage, the data model and the API are documented in `README.md`. `USER_MANUAL.md` is the end-user guide. `clinical-genogram-claude-code-prompt.md` is the original spec the project was generated from. It describes some files (e.g. `test/*.spec.tsx`) that don't exist.

## Commands

```bash
npm install
npm start              # stencil build --dev --watch --serve (serves www/, src/index.html)
npm run build          # production build -> dist/, loader/, www/
npm test               # stencil test --spec (Jest)
npx stencil test --spec -- src/core/GenogramState.spec.ts   # single spec file
npm run generate       # scaffold a new component
```

- Spec files live next to the source (`src/core/*.spec.ts`). `LayoutEngine.spec.ts` lays out the `demo/sample-data` files, so changes to the samples can affect it. `consanguinity-family.json` (five generations: uncle–niece, double first cousins, first cousins, once removed, second cousins, half cousins) is the stress test for loops.
- There is no lint script. Type-checking runs as part of `stencil build`, and `tsconfig` has `strict`, `noUnusedLocals` and `noUnusedParameters` on, so an unused import fails the build.
- `src/components.d.ts` is auto-generated by Stencil on build. Don't hand-edit it.
- Demos: `demo/vanilla-demo/index.html` loads `dist/clinical-genogram/clinical-genogram.esm.js`, so build first. Sample data in `demo/sample-data/` is copied into `www/demo/sample-data` by the `www` output target.
- Angular/React/Vue output targets in `stencil.config.ts` are only active if `@stencil/{angular,react,vue}-output-target` is installed (they are required inside a `try`). Generated proxies go to `output-targets/*`.

## Architecture

**Framework-agnostic core (`src/core/`) + thin Stencil views.** All state and logic live in plain TS classes with a `subscribe(fn) => unsubscribe` pattern. Components hold manager instances and copy data into `@State` fields inside subscriber callbacks.

- `GenogramState`: source of truth (`Map`s of persons and relationships). Every mutating CRUD method calls `saveSnapshot()` (a `structuredClone` into `HistoryManager`, 50-step limit) and then `notify()`. **Exception:** `updatePersonPosition()` is silent: no snapshot, no notify. It's used for drag and layout, followed by one `notifyChange()`. Keep this distinction when adding mutations, or undo history gets polluted.
- `LayoutEngine` = `GenerationCalculator` + `PositionResolver`. The calculator assigns rows by relaxing three rules that only ever move people down: a child is below each parent, ancestors sit just above their nearest child, and partners share a row. So in-law families line up with their partner, and in a couple from different generations (uncle–niece, cousins once removed) the older partner is drawn on the younger one's row. The proband is row 0, and people with no links stay on the proband's row. The resolver groups partners in a row into rigid blocks, orders blocks with barycentre sweeps so sibling groups stay contiguous, then refines x by solving a weighted isotonic regression per row (`isotonicWithGaps`). Array order of `persons` breaks ties in row order. Spacing constants are in `src/utils/constants.ts`. `calculateLayout` also **mutates the Person objects passed in**.
- `KinshipBuilder` (`buildGenogramFromIntake`) turns an `IntakeForm` (questionnaire answers, every relative described relative to the patient; `src/types/intake.ts`) into `GenogramData`. It is pure and UI-free so other input sources can reuse it. It creates placeholder persons (`isPlaceholder`) where structure needs them, for example the other parent of a half-sibling or the other grandparent of a half aunt (`IntakeChild.parentage`). Every keyed entry is created up front (`precreateKeyed`), so any partner's `linkedRelativeKey` resolves to the same person whichever part of the form it was entered in. Siblings' `partners` give nephews and nieces. It also emits persons in left-to-right order per generation.
- `GenogramState.setData` doesn't record history (initial loads); `replaceData` does (questionnaire submit).
- Family edits (`addParents`, `addSibling`, `addPartner`, `addChild`, `setParents`, `removeChildFromCouple`, `moveChild`) are one snapshot each. They use the private no-snapshot helpers `insertPerson` / `insertCouple` / `patchRelationship`, and `setParents` refuses cycles (`getPossibleParentCouples`). Every structural mutation, and `setData`, runs `refreshAutoConsanguinity()`. It fills in or clears a couple's blood relationship from the tree only when `consanguinityAuto` is true, or when nothing is recorded yet. `updateRelationship` with consanguinity fields marks the value as set by a person (`consanguinityAuto: false`). `<clinical-genogram>` re-runs the layout after family edits from the side panel.
- **Birth order.** `src/utils/birth-order.ts` (`birthKey`, `sortByBirth`) keeps every couple's `childrenIds` oldest first, and the layout draws siblings in `childrenIds` order. `GenogramState.refreshBirthOrder()` runs in `setData`, `updatePerson`, `add/updateRelationship` and every family edit (`finishFamilyEdit`), and `KinshipBuilder` sorts its output too. Only children with a known age are reordered (among the slots they hold); the rest keep their hand-set place. `moveChild` refuses a swap of two aged children (`canMoveChild`). `<clinical-genogram>` re-runs the layout after a person edit only when some `childrenIds` order changed.
- `SelectionManager` (one person or one relationship, mutually exclusive), `DragManager`, `ZoomPanManager` (zoom/pan state, `screenToWorld`, `fitToView`).

**Component tree.** `<clinical-genogram>` (`src/components/clinical-genogram/`) is the only public element and the only one with `shadow: true`. It owns all the managers and passes them **by reference as props** to `<genogram-canvas>`. It wires toolbar, canvas and property-panel custom events to state mutations, and exposes the public `@Method`s and `@Event`s. It re-renders via a `stateVersion` counter that its state subscription bumps. Every other component uses `shadow: false`. This is required for `person-node` and `relationship-edge`, which render inside the SVG. Internal event names are prefixed (`canvasNodeClick`, `toolbarUndo`, …) and re-emitted publicly as `nodeClick`, etc.

**Rendering is function-based, not component-based.** `src/symbols/index.tsx` composes a person's glyph: a base shape by gender and type, then overlays (adopted, foster, deceased, condition quadrants). Up to 4 conditions fill their `quadrant` (a condition without one, or sharing one, takes the next free quarter). With 5 or more, `renderSlices` in `condition-indicator.tsx` splits the symbol into equal pie slices, quartered conditions first (`orderConditionSlices` in `src/symbols/index.tsx`), capped at `MAX_CONDITION_SLICES` (6): with more, the 6th slice is a grey "+N" (its hover title lists the hidden ones). With `showConditionIcons`, each quarter or slice also gets an icon from `src/symbols/condition-icons.tsx` (`matchConditionIcon`: the explicit `icon`, else keyword rules on the name with the first match winning, else the first letter). Names and ages are drawn below the symbol, and `src/utils/bounds.ts` (`contentBounds`) includes them for fit-to-view. Lines from a couple to their children come from `src/utils/connectors.ts`. `computeFamilyConnectors` stacks overlapping rails into lanes (widest highest), and `buildConnectorPath` adds rounded corners, hops where a vertical crosses another family's rail, and junction points (drawn as dots). Hovering over or selecting a person highlights their couples and family lines and fades the rest (`focusRelationshipIds`). The old `src/lines/child-line.tsx` is no longer used by the canvas. The canvas also draws the generation bands (from `person.generation`, set by the layout), the proband arrow and the selection halo. Placeholders get a dashed outline via `SymbolOptions.dashed`, and the soft symbol shadow is a CSS `drop-shadow` in `genogram-canvas.css`, so it isn't included in PNG export. `src/lines/dispatcher.ts` maps each `RelationshipType` to a `render*Line(opts)` function, one file per type. Separation and divorce variants reuse `zigzag-pattern.tsx`. To add a relationship type: add it to `src/types/relationships.ts`, create the line file, add a case to the dispatcher, and update the legend and the relationship form.

**Templates.** `src/core/templates.ts` holds `GENOGRAM_TEMPLATES`: common family structures, each an `IntakeForm` for a given patient gender with role labels as names, built by `buildTemplate` through `KinshipBuilder`. The toolbar's Templates menu emits `toolbarApplyTemplate`, which calls the public `loadTemplate()` (`replaceData`, so one undo step).

**Questionnaire.** `<genogram-intake-wizard>` (opened by the toolbar's "Generate" button) is rendered by `<clinical-genogram>` as an overlay. It previews the result with its own `GenogramState` and managers and a second `<genogram-canvas>`. Submitting goes through the public `loadIntake()` method. On an empty board, the last answers are kept so reopening continues from them.

**Edit mode.** With people on the board, `openIntake()` reads the tree back with `intakeFromTree` (`src/core/IntakeFromTree.ts`) from the proband, or shows a patient picker first. Every entry's `key` is the person's id, and the builder uses keys as ids. Unshown details travel in `IntakeRelative.extra` and `IntakePartner.coupleExtra`. Half relatives carry their named `otherParent`. On submit, `mergeKept` puts back people the questionnaire never held (`placedIds`), plus partners removed only because they sat inside a removed card (`partnerOnlyIds`). It also keeps their relationships, deduplicated by partner pair.

**Consanguinity.** A couple stores a genetic degree (`consanguinity`) and an optional plain-language `consanguinityRelation`. `src/utils/consanguinity.ts` holds the mapping between them, the labels, and `deriveConsanguinity()`, which works the relation out from parent links via the nearest common ancestor. `KinshipBuilder` runs it on every couple after building, so a partner linked to a relative (`linkedRelativeKey` → intake `key`) gets the relation from the tree, overriding the manual answer. The canvas draws the marker line with the couple, and the labels in a separate layer above the person nodes.

**Names.** A person has a single `fullName`. `src/utils/migrate.ts` (`migratePerson`) converts legacy `firstName`/`lastName` data and is applied in `GenogramState.setData` and `importFromJson`. `src/utils/name.ts` (`splitName`) wraps the name onto two lines in the canvas.

**Types** live in `src/types/` (`nodes.ts`, `relationships.ts`, `schema.ts`, re-exported from `index.ts`). `src/index.ts` exports the types plus `GenogramState`, `LayoutEngine` and `buildGenogramFromIntake` for programmatic use.

**Export/import** (`src/utils/`): `export-json`, `export-png` (SVG serialisation → canvas → blob), `export-pdf` (dynamic `import('jspdf')` over the PNG output), and `import-json` + `json-schema` (validation and version migration).

## Known gaps

These are gaps in the current code, not intended behaviour:
- The public `exportAs()` method handles only `'json'`. `'png'` and `'pdf'` return the raw data. The toolbar calls `downloadPng` directly, and `exportToPdf` isn't wired to anything.
- The toolbar's JSON import calls `JSON.parse` + `setData` directly, which skips `importFromJson` validation.
- The "link mode" relationship flow (toolbar → click two nodes) always creates a `'marriage'`. The user changes the type afterwards in the property panel.
- Twins are stored (`twinGroupId`, `isIdenticalTwin`, set by the questionnaire), but the canvas doesn't draw a twin connector yet. `renderTwinsConnector` exists in `src/symbols/` but nothing calls it.
- Adding a person from the toolbar records two undo steps: `addPerson`, then `updatePerson` for its position.
